A6 (proposed by beta-f2-2, E1): generator capability matrix, web-tool audit, repair-table additions, sensitivity analyses

Status: proposed text for protocol section 15. Written 2026-11-21 08:50 while the E1 campaign is running (generated so far: 28 valid runs + 6 pilots; no confirmatory analysis has been read; analysis.py was executed twice on partial data, at ~07:39 on 13 runs as a pipeline smoke test and at ~08:50 on 13 runs to test the sensitivity table; both outputs were seen; items 1 to 5 come from harness events (the allow-list pilot failure, the lock deadlock, the JDK 21 host build failures), not from any E1 result, and the sensitivity variants are the generic ones any reader would ask for).

1. Capability matrix. The three bundles gave the generator different means during a run. claude-haiku: file tools only (Read, Edit, Write, Glob, Grep), no shell, no web tool. codex-luna: a shell, sandbox off, writes contained by the Landlock write-jail, network not blocked by the jail. agy-g38flash: a shell restricted to an allow-list (shared launcher read-only set + E1 extras: mkdir touch chmod cp mv rm java javac kotlinc uname date whoami); curl, wget, npm, pip, gradle, adb stay denied; headless mode ends the run at the first denied command. The extras were added after the pilot showed an agy run ending empty on 'java -version' (invalid for a harness reason, and style-dependent). From the switch-over time recorded in runs.csv (column web_denied, generated_at) agy runs also run under f2-4's web-deny hook; earlier agy runs (web_denied = n) had web tools available. No run built or ran the app (audited from executed commands); claude had no shell and agy's allow-list denied build tools, while codex had an open shell and was only audited.
2. Web-tool audit (R2, no-retrieval scope). Every run is audited from its transcript by tool invocation, not only by command string: agy search_web / read_url* / execute_url / browser_*, codex web_search items, claude WebSearch / WebFetch. Counts are runs.csv web_tool_calls and web_tools; attempts count even when a hook denied them. Result so far: 0 attempts in all generated runs (pilot + campaign, all bundles). A run with web_tool_calls > 0 is reported and excluded in the sensitivity analysis below, not in the primary one.
3. Sensitivity analyses, added, none replaces a confirmatory endpoint: (a) C1-C3 without any run that has web_tool_calls > 0; (b) C1-C3 per bundle and leave-one-bundle-out, so one bundle cannot drive the pooled result unseen; (c) compile-excluded: C1-C3 over runs whose source builds (zero-touch or after table repairs), reported beside the build pass rate per bundle x style, because a draft that does not compile is analysed at source level in the primary analysis (R7) and may differ in size and structure.
4. R7 repair table, additions logged in results/repairs.csv and counted in the 3-repair cap: JDK toolchain request not installed -> 17; kotlin.jvm.target.validation.mode=warning on 'Inconsistent JVM-target compatibility'; missing import from a fixed name -> FQN table for 'Unresolved reference'. Gradle itself runs on JDK 17 (JAVA_HOME), JDK 17 and 21 are registered for toolchains. Repairs touch the build copy only; the analysed source is the generated source. A first build pass on a JDK 21 host showed the host JDK decided pass or fail for 'Inconsistent JVM-target', which is why the table repair exists; those builds were discarded and redone.
5. Size normaliser: codex drafts are dense (one pilot: 92 LOC in 13 KB, lines up to 1313 chars). C3 stays per 1000 LOC as frozen; analysis.py also reports per 100k non-whitespace code characters as a labelled sensitivity line.
6. Decided before outcome data: yes for items 1 to 5, with the disclosure in the status line above.
